Introducción

¿Qué es GitFlow?

GitFlow es un modelo de ramificación (branching model) para Git, propuesto por Vincent Driessen en 2010.


Define un conjunto estricto de reglas sobre cómo y cuándo crear ramas, qué se fusiona con qué, y cuándo se puede hacer un release. Es especialmente útil en proyectos con versiones planificadas y equipos medianos o grandes.


No es una herramienta

GitFlow es una convención. Se puede seguir con comandos git puros o con herramientas como git-flow (extensión CLI).

El problema que resuelve

  • 1
    Caos en el historial
    Sin convención, todos hacen push a main y el historial es ilegible.
  • 2
    Releases accidentales
    Código incompleto llega a producción porque no hay separación.
  • 3
    Hotfixes complejos
    Un bug urgente en producción se complica por features a medio terminar.
  • ✓
    GitFlow da estructura
    Cada tipo de trabajo tiene su rama, su ciclo de vida y su destino.

    Las 5 ramas de GitFlow

    main

    Código en producción. Solo recibe merges de release/* y hotfix/*. Cada commit en main es un release oficial. Se tagea con la versión.

    develop

    La rama de integración. Aquí confluyen todos los features terminados. Es el "próximo release". Se bifurca desde main inicialmente y vive para siempre.

    feature/*

    Una rama por cada nueva funcionalidad. Sale de develop y vuelve a develop. Nombre: feature/login, feature/pagos, etc.

    release/*

    Preparación de un release. Sale de develop, se hacen ajustes finales, y se mergea a main y develop. Nombre: release/1.2

    hotfix/*

    Corrección urgente en producción. Sale directo de main y se mergea a main y develop. Nombre: hotfix/crash-login

    Regla de oro

    Nunca hacer commits directamente en main.

    Solo llegan merges controlados desde release o hotfix.

    Flujo de trabajo

    El ciclo de vida de un Feature

    • 1
      Crear la rama
      Desde develop se bifurca feature/mi-feature
    • 2
      Desarrollar
      Commits en la rama del feature. Nadie más se ve afectado.
    • 3
      Pull Request / Code Review
      Se solicita revisión antes de mergear (buena práctica).
    • 4
      Merge a develop
      Con --no-ff para preservar el historial. Se elimina la rama.
    • 5
      Release
      Cuando hay suficientes features, se abre release/X.Y desde develop.
    • 6
      Cierre del release
      Merge a main con tag de versión, y back-merge a develop.
    ciclo-feature.sh
    ## PASO 1: Iniciar feature desde develop
    $ git checkout develop
    $ git checkout -b feature/login
    Switched to a new branch 'feature/login'

    ## PASO 2: Desarrollar y commitear
    $ git add . && git commit -m "feat: add login form"
    [feature/login abc1234] feat: add login form

    ## PASO 4: Merge a develop (--no-ff)
    $ git checkout develop
    $ git merge --no-ff feature/login -m "merge: feature/login"
    $ git branch -d feature/login
    ✓ Rama eliminada correctamente

    ## PASO 5: Abrir release
    $ git checkout -b release/1.0 develop
    ## PASO 6: Cerrar release
    $ git checkout main && git merge --no-ff release/1.0
    $ git tag -a v1.0 -m "Release 1.0"
    $ git checkout develop && git merge --no-ff release/1.0
    Casos especiales

    Hotfix: bug urgente en producción

    El hotfix es el único flujo que sale directamente de main. Permite corregir un bug crítico sin esperar el próximo release, y sin mezclar features incompletos.

    Regla del hotfix

    Al terminar, se mergea a main (con tag) y también a develop. Esto garantiza que el fix no se pierda en el próximo release.

    # Desde main, crear hotfix
    git checkout -b hotfix/crash-login main
    # ... corregir el bug ...
    git commit -m "fix: null pointer in auth"

    # Mergear a main y tagear
    git checkout main
    git merge --no-ff hotfix/crash-login
    git tag -a v1.0.1 -m "Hotfix: crash login"

    # CRUCIAL: también a develop
    git checkout develop
    git merge --no-ff hotfix/crash-login
    ✓ Fix propagado en ambas ramas
    Evaluación

    Ventajas y desventajas

    ✓ Ventajas

    Separa claramente el código de producción del de desarrollo.
    Soporta múltiples versiones en paralelo (ej: v1 y v2 simultáneas).
    Los hotfixes no interfieren con features en desarrollo.
    El historial de Git queda muy explícito sobre qué cambio y cuándo.
    Ideal para proyectos con releases planificados y equipos grandes.
    Integra bien con CI/CD al tener puntos de integración claros.

    ✗ Desventajas

    Overhead alto: muchas ramas y merges pueden ser pesados para equipos chicos.
    En proyectos con despliegue continuo (CD) puede sentirse excesivo.
    Curva de aprendizaje para quienes vienen de flujos más simples.
    El historial con --no-ff puede ser verboso en repos muy activos.
    Para proyectos con un solo developer o prototipos, es sobrediseñado.

    ¿Cuándo NO usar GitFlow?

    Si el equipo hace deploys múltiples veces por día, considerar GitHub Flow o Trunk-Based Development, que son más livianos.

    gitflow-demo.sh — paso a paso
    ## 1. INICIALIZAR EL REPO
    $ mkdir proyecto-demo && cd proyecto-demo
    $ git init && echo "# App" > README.md
    $ git add . && git commit -m "chore: init repo"
    $ git branch -M main

    ## 2. CREAR RAMA DEVELOP
    $ git checkout -b develop
    Switched to a new branch 'develop'

    ## 3. FEATURE: login
    $ git checkout -b feature/login develop
    $ echo "login()" > auth.py && git add . && git commit -m "feat: add login"
    $ echo "logout()" >> auth.py && git commit -am "feat: add logout"

    ## 4. MERGE FEATURE → DEVELOP
    $ git checkout develop
    $ git merge --no-ff feature/login -m "merge: feature/login → develop"
    $ git branch -d feature/login

    ## 5. RELEASE 1.0
    $ git checkout -b release/1.0 develop
    $ echo "1.0.0" > VERSION && git add . && git commit -m "chore: bump version 1.0.0"
    $ git checkout main && git merge --no-ff release/1.0 -m "release: v1.0"
    $ git tag -a v1.0 -m "Release 1.0"
    $ git checkout develop && git merge --no-ff release/1.0 -m "back-merge: release/1.0"
    $ git branch -d release/1.0

    ## 6. HOTFIX: bug en producción
    $ git checkout -b hotfix/null-crash main
    $ echo "fix: check null" >> auth.py && git commit -am "fix: null crash on login"
    $ git checkout main && git merge --no-ff hotfix/null-crash -m "hotfix: null-crash"
    $ git tag -a v1.0.1 -m "Hotfix: null crash"
    $ git checkout develop && git merge --no-ff hotfix/null-crash
    $ git branch -d hotfix/null-crash

    ## 7. VER EL GRAFO FINAL
    $ git log --oneline --graph --all --decorate
    * abc1234 (HEAD -> develop) merge: hotfix/null-crash
    |\
    | * def5678 (tag: v1.0.1, main) hotfix: null-crash
    |/
    * ghi9012 back-merge: release/1.0
    * jkl3456 (tag: v1.0) release: v1.0
    * mno7890 merge: feature/login → develop
    * pqr1234 chore: init repo
    ✓ Historial explícito y trazable
    Contexto

    GitFlow vs otros modelos

    MODELO RAMAS PRINCIPALES IDEAL PARA COMPLEJIDAD
    GitFlow main, develop, feature, release, hotfix Releases planificados, equipos medianos/grandes ●●● Alta
    GitHub Flow main + feature branches + PR CD/despliegue continuo, equipos ágiles ●●● Baja
    Trunk-Based main (trunk) + short-lived branches Alta frecuencia de deploy, feature flags ●●● Media
    GitLab Flow main + feature + environment branches Múltiples ambientes (dev, staging, prod) ●●● Media

    Conclusión clave

    No existe el modelo "mejor". GitFlow brilla cuando la empresa hace versiones numeradas (ej: app móvil, librería open-source, software empaquetado). Para SaaS con CI/CD agresivo, GitHub Flow o Trunk-Based son superiores.
